# 藍牙被系統中斷後重連無聲 / 崩潰 —— 研究記錄

日期：2026-09-12。分支：`research/bt-interrupt-no-sound`。
環境：Windows 11 22631、MediaTek 藍牙適配器、一加 Ace 5 與華為 MatePad 11（皆為已配對的 A2DP 來源端）。

## 症狀（用戶回報）

設備遠離（或其它系統中斷）之後再連接，連接顯示成功但沒有聲音；需要手動「先斷開、再重連」才能恢復。

## 重現方法

`tools/probe/probe.exe --bt off` / `--bt on`（用 WinRT Radio API 開關藍牙無線電，模擬系統層級的中斷；無需管理員權限）。流程：

1. 啟動程式連接設備（健康狀態：A2DP SNK 捕獲端點 **ACTIVE**）。
2. `--bt off` → worker 收到 Closed 正常退出，端點變 **NOTPRESNT**。
3. `--bt on` → 藍牙鏈路恢復（ACL + AVRCP 回來），端點變 **UNPLUGGED**（未激活，等連接）。
4. 重新連接。重複多次。

## 發現

中斷之後的「下一次開啟」有兩種失效模式，隨機出現：

1. **崩潰**：worker 在開啟途中（~2s）以 0xC0000005 存取違規死亡。
   事件日誌顯示出錯模組是 **`Windows.Media.Devices.dll` +0x52c89**——
   即系統的 `AudioPlaybackConnection` 實作內部，不是本程式的程式碼。
   （02:22、02:39、02:59、03:15 四次崩溃，同一偏移。）
2. **無聲連接**：`OpenAsync` 回報 Success、worker 進入等待迴圈，
   但 A2DP SNK 端點停在 **UNPLUGGED**——音訊通路沒有建立。
   使用者看到「已連接」，手機播放卻沒有聲音。這就是回報的症狀。

### 楔住狀態很頑固

以下手段全部無法把端點拉回 ACTIVE（每項都實測過）：

- 關閉 → 立即重開（~0.25s 間隔，3 次）
- 關閉 → 等 2.5s / 15s / 30s → 重開
- 關閉 → 再翻一次無線電 → 等 30s → 重開
- 無連接狀態下翻無線電 → 等 20s（讓手機先回連）→ 開啟
- 保持連接開著 5 分鐘以上（等手機端自動重試）

而且楔住會「傳染」：系統只有一份 A2DP sink，進入楔住狀態後連從未經歷中斷的
另一台設備（MatePad 11）開啟也會同樣崩潰/無聲。

### 用戶「手動斷開再重連」為什麼有效（推斷）

手動恢復發生在真實的「走遠」場景（無線電一直開著），與本實驗的「無線電級中斷」
對系統狀態的破壞程度不同；且人工操作的時間尺度更長。真正的恢復手段很可能在
系統層：重啟藍牙支援服務、停用/啟用適配器、重新配對或重啟——這些都需要管理員
權限或破壞性操作，本程式（以普通權限運行的托盤程式）做不了，也不該做。

## 程式能做什麼（本分支的改動）

楔住本身救不了，但可以不再「演裝連上了」：

1. **端點驗證**（worker，`WaitForA2dpEndpointActive`）：`OpenAsync` 成功後，
   用 `FindAllAsync(DeviceClass::AudioCapture)`（只回報激活端點）輪詢最多 8 秒，
   確認「<裝置名稱> A2DP SNK」端點真的激活。沒有就帶新結束碼
   `APC_E_ENDPOINT_NOT_ACTIVE` (0xA0000004) 退出，連線物件正常解構。
   列舉本身失敗時放行（防禦性檢查不能反過來弄壞正常連線）。
2. **自動重試**（父行程，`WM_WORKEREXITED`）：對兩種暫時性失敗——
   開啟途中被系統打斷崩潰 (0xC0000005)、端點未激活 (APC_E_ENDPOINT_NOT_ACTIVE)——
   自動重試最多 2 次（沿用 `AUTORECONNECT_DELAY_MS`），仍失敗則顯示
   可重試的錯誤。實測崩潰與楔住各佔一半，重試對「崩潰」變體確實有效
   （02:22 崩潰後 02:23 同場景的開啟就成功了）；對「楔住」變體重試會正確地
   以錯誤收場，不再無限循環。
3. `g_connectAttempts`：每設備連續暫時性失敗計數，連線成功即清零。
4. 研究用日誌（`SettingsUtil.hpp` 的 `DebugLog`，%TEMP%\apc_debug.log）與
   探針工具（`tools/probe`）。合入主線前可整體拿掉。

## 給使用者的驗證方法

1. 正常路徑回歸：無中斷時連接，托盤菜單/picker 應顯示已連接，probe 應顯示端點 ACTIVE。
2. 製造中斷：`probe.exe --bt off` 等 5 秒、`--bt on`（或真實走遠再回來）。
3. 之後點連接：
   - 若系統選了「崩潰」變體：介面上會自動重試，多半直接恢復；
   - 若系統選了「楔住」變體：約 20 秒後（8s 端點輪詢 × 3 次嘗試 + 間隔）
     顯示「Connected, but the audio endpoint is not ready」+ 重試按鈕——
     這是誠實的失敗。此時需要系統層恢復（重啟藍牙服務/重新配對/重啟系統），
     或等系統自己把端點吐出來。

## 開放問題

- 楔住狀態跨重啟是否還在？（若 AudioEndpointBuilder 持久化壞狀態則重啟才修。）
- 真實「走遠」場景（無線電不關）是否同樣出現這兩種失效？本實驗只能用無線電開關近似。
- Windows.Media.Devices.dll+0x52c89 的崩潰值得留一份帶符號的轉儲回饋給微軟。

## 真機驗證補充（2026-09-12 晚，用戶實測）

用戶在真機（手機關/開藍牙模擬中斷）測試：三次重連都報
"Connected, but the audio endpoint is not ready"，但**第二次重連時實際已有聲音**。

結論修正：

1. 名稱匹配的端點檢查會**誤報**——端點已激活（有聲音）但
   `endpoint.Name().find(deviceName)` 沒命中（FriendlyName 的空格/形式與
   DeviceInformation.Name 不一致）。已改為 **MAC 匹配**：端點的
   `System.Devices.DeviceInstanceId`（BTHENUM\DEV_<MAC>...）對 worker deviceId
   裡解析出的 12 位 MAC，大小寫歸一後比对。這個匹配不依賴顯示名稱。
2. 端點激活可能超過 8 秒，等待窗口放寬到 30 秒。
3. 端點失敗的重試間隔從 2.5s 拉長到 10s（連續立刻重試都在楔住窗口裡）。
4. 無線電級中斷（實驗室重現手法）造成的楔住仍然頑固：崩潰與 UNPLUGGED 反覆出現，
   手機側 `svc bluetooth disable/enable` 也清不掉。真實「走遠」場景較溫和，
   重試即可恢復（用戶實測第 2 次有聲音）。
