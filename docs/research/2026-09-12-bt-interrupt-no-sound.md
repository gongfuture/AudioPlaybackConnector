# 蓝牙被系统中断后重连无声 / 崩溃 —— 研究记录

日期：2026-09-12。分支：`research/bt-interrupt-no-sound`。
环境：Windows 11 22631、MediaTek 蓝牙适配器、一加 Ace 5 与华为 MatePad 11（皆为已配对的 A2DP 来源端）。

## 症状（用户回报）

设备远离（或其它系统中断）之后再连接，连接显示成功但没有声音；需要手动"先断开、再重连"才能恢复。

## 重现方法

`tools/probe/probe.exe --bt off` / `--bt on`（用 WinRT Radio API 开关蓝牙无线电，模拟系统级的中断；无需管理员权限）。流程：

1. 启动程序连接设备（健康状态：A2DP SNK 捕获端点 **ACTIVE**）。
2. `--bt off` → worker 收到 Closed 正常退出，端点变 **NOTPRESNT**。
3. `--bt on` → 蓝牙链路恢复（ACL + AVRCP 回来），端点变 **UNPLUGGED**（未激活，等连接）。
4. 重新连接。重复多次。

## 发现

中断之后的"下一次开启"有两种失效模式，随机出现：

1. **崩溃**：worker 在开启途中（~2s）以 0xC0000005 访问违例死亡。
   事件日志显示出错模块是 **`Windows.Media.Devices.dll` +0x52c89**——
   即系统的 `AudioPlaybackConnection` 实现内部，不是本程序的代码。
   （02:22、02:39、02:59、03:15 四次崩溃，同一偏移。）
2. **无声连接**：`OpenAsync` 报告 Success、worker 进入等待循环，
   但 A2DP SNK 端点停在 **UNPLUGGED**——音频通路没有建立。
   用户看到"已连接"，手机播放却没有声音。这就是回报的症状。

### 卡住状态很顽固

以下手段全部无法把端点拉回 ACTIVE（每项都实测过）：

- 关闭 → 立即重开（~0.25s 间隔，3 次）
- 关闭 → 等 2.5s / 15s / 30s → 重开
- 关闭 → 再翻一次无线电 → 等 30s → 重开
- 无连接状态下翻无线电 → 等 20s（让手机先回连）→ 开启
- 保持连接开着 5 分钟以上（等手机端自动重试）

而且卡住会"传染"：系统只有一份 A2DP sink，进入卡住状态后连从未经历中断的
另一台设备（MatePad 11）开启也会同样崩溃/无声。

### 用户"手动断开再重连"为什么有效（推断）

手动恢复发生在真实的"走远"场景（无线电一直开着），与本实验的"无线电级中断"
对系统状态的破坏程度不同；且人工操作的时间尺度更长。真正的恢复手段很可能在
系统层：重启蓝牙支持服务、停用/启用适配器、重新配对或重启——这些都需要管理员
权限或破坏性操作，本程序（以普通权限运行的托盘程序）做不了，也不该做。

## 程序能做什么（本分支的改动）

卡住本身救不了，但可以不再"演装连上了"：

1. **端点验证**（worker，`WaitForA2dpEndpointActive`）：`OpenAsync` 成功后，
   用 `FindAllAsync(DeviceClass::AudioCapture)`（只回报激活端点）轮询最多 8 秒，
   确认"<设备名称> A2DP SNK"端点真的激活。没有就带新结束码
   `APC_E_ENDPOINT_NOT_ACTIVE` 退出，连接对象正常析构。
   枚举本身失败时放行（防御性检查不能反过来弄坏正常连接）。
2. **自动重试**（父进程，`WM_WORKEREXITED`）：对两种暂时性失败——
   开启途中被系统打断崩溃 (0xC0000005)、端点未激活 (APC_E_ENDPOINT_NOT_ACTIVE)——
   自动重试最多 2 次（沿用 `AUTORECONNECT_DELAY_MS`），仍失败则显示
   可重试的错误。实测崩溃与卡住各占一半，重试对"崩溃"变体确实有效
   （02:22 崩溃后 02:23 同场景的开启就成功了）；对"卡住"变体重试会正确地
   以错误收场，不再无限循环。
3. `g_connectAttempts`：每设备连续暂时性失败计数，连接成功即清零。
4. 研究用日志（`SettingsUtil.hpp` 的 `DebugLog`，%TEMP%pc_debug.log）与
   探针工具（`tools/probe`）。合入主线前可整体拿掉。

## 给用户的验证方法

1. 正常路径回归：无中断时连接，托盘菜单/picker 应显示已连接，probe 应显示端点 ACTIVE。
2. 制造中断：`probe.exe --bt off` 等 5 秒、`--bt on`（或真实走远再回来）。
3. 之后点连接：
   - 若系统选了"崩溃"变体：界面上会自动重试，多半直接恢复；
   - 若系统选了"卡住"变体：约 20 秒后（8s 端点轮询 × 3 次尝试 + 间隔）
     显示"Connected, but the audio endpoint is not ready"+ 重试按钮——
     这是诚实的失败。此时需要系统层恢复（重启蓝牙服务/重新配对/重启系统），
     或等系统自己把端点吐出来。

## 开放问题

- 卡住状态跨重启是否还在？（若 AudioEndpointBuilder 持久化坏状态则重启才修。）
- 真实"走远"场景（无线电不关）是否同样出现这两种失效？本实验只能用无线电开关近似。
- Windows.Media.Devices.dll+0x52c89 的崩溃值得留一份带符号的转储反馈给微软。

## 真机验证补充（2026-09-12 晚，用户实测）

用户在真机（手机关/开蓝牙模拟中断）测试：三次重连都报
"Connected, but the audio endpoint is not ready"，但**第二次重连时实际已有声音**。

结论修正：

1. 名称匹配的端点检查会**误报**——端点已激活（有声音）但
   `endpoint.Name().find(deviceName)` 没命中（FriendlyName 的空格/形式与
   DeviceInformation.Name 不一致）。已改为 **MAC 匹配**：端点的
   `System.Devices.DeviceInstanceId`（BTHENUM\DEV_<MAC>...）对 worker deviceId
   里解析出的 12 位 MAC，大小写归一后比对。这个匹配不依赖显示名称。
2. 端点激活可能超过 8 秒，等待窗口放宽到 30 秒。
3. 端点失败的重试间隔从 2.5s 拉长到 10s（连续立刻重试都在卡住窗口里）。
4. 无线电级中断（实验室重现手法）造成的卡住仍然顽固：崩溃与 UNPLUGGED 反复出现，
   手机侧 `svc bluetooth disable/enable` 也清不掉。真实"走远"场景较温和，
   重试即可恢复（用户实测第 2 次有声音）。
